# Plan 64 — PWA 加固与真实设备验收

本文件保留尚未结束的验收范围，项目级状态只在 [ROADMAP](../../ROADMAP.md) 维护。2026-08-24 的完整确认方案已保存为[历史快照](../completed/20260824-pwa-hardening.md)；本次整理不改变产品行为，也不将缺失的设备验收标记为通过。

## 当前依据与剩余边界

Serwist、离线应用壳和同源多标签连接控制已有实现，来源包括提交 `9b70dad`、`d2ac793` 及当前源码。后续 Protocol v2 和 endpoint 模型替代了早期 room、本地无限历史以及 partial 持久化假设，不能继续按这些旧规则重新实施。

当前结构、业务存储和缓存边界以 [ARCHITECTURE](../../ARCHITECTURE.md) 为准；协议以 [PROTOCOL](../../../PROTOCOL.md) 为准。当前设计基线见 [DESIGN](../../DESIGN.md)，素靛主题是另一个尚未实施的方案，不是本项验收的前置条件。

以上代码与历史记录不是本轮重新运行测试的结果。未取得真实设备、浏览器版本和操作证据前，不宣称移动端验收完成。

## 设备验收范围

延续原方案的浏览器范围：Chrome/Edge 桌面端、Chrome Android、最近两个版本的 iOS Safari。iOS Chrome 至少进行功能兼容 smoke；只有另行明确将其安装路径列为正式支持能力时，才增加对应发布门槛。

| 环境 | 需要记录的关键流程 |
| --- | --- |
| iOS Safari | 添加到主屏幕、standalone 启动、已缓存壳的断网冷启动、本地正式历史读取、恢复联网 |
| Android Chrome | 安装、普通与 maskable 图标裁剪、standalone 启动、断网冷启动及恢复联网 |
| iOS Chrome | 网页访问、Service Worker/IndexedDB 能力、扫码权限及实际添加到主屏幕行为 |
| 两类移动设备 | 摄像头授权与拒绝、扫码、移动键盘、安全区、切后台、锁屏或系统挂起后的前台恢复 |

验收必须使用当前 endpoint/device-scoped pairing，不再操作旧 Room 模型。离线时只检查已缓存资源和正式历史可读，以及发送与在线操作被禁用；不要求保持后台 WebSocket，也不要求恢复未持久化的 partial 或离线发送。

新版 Worker 的验收要区分后台安装、更新提示和用户主动刷新；不能通过强制刷新掩盖草稿或流式状态被中断的问题。IndexedDB 不可用时，应核对实际错误和恢复提示，不将生成临时身份作为成功路径。

## 执行前提与记录

开始实际验收前另行确认测试环境、真实设备、浏览器 profile、Pi 身份、操作范围和模型用量。本文不是启动服务、执行模型调用或发布生产的授权。

验收记录至少包含：

- 设备、操作系统与浏览器版本，以及普通网页或 standalone 模式；
- 受测提交/构建、经过脱敏的环境说明和操作步骤；
- 每项结果、失败复现条件、必要截图或日志；
- 临时身份、profile、服务与测试数据的清理结果。

截图、日志和一次性证据放在 `.pi/tmp/`，长期方案只保留脱敏结论和必要引用，不写二维码、token、身份私钥或真实业务消息。

## 完成与停止条件

原方案的移动发布门槛保留：自动化验收通过，且至少一台真实 iOS 设备与一台真实 Android 设备的关键流程通过。没有真实设备时，只能声明实际取得的自动化或 Chromium 证据，并明确移动端未验证。

完成前先核对受影响的当前自动化基线，再补齐设备记录。若遇到浏览器能力限制、行为缺陷或必须改变产品边界的问题，先报告事实并确认后续范围；本项不能顺带引入 Push、账号、离线队列、原生客户端或新主题。

收口顺序：将仍有效的支持边界同步到长期文档，归档本验收方案，最后更新 ROADMAP。归档前不得用“核心代码已有实现”替代尚缺的设备证据。
